  "content": "## Designing an “official‑source‑first” Crawler for CBE & FRA‑Supervised Institutions  \n\nI approached the task as if I were building the system myself, beginning with the data I must collect, then ranking the authoritative sources, and finally wiring the technical pipeline while staying inside Egypt’s regulatory walls.\n\n---\n\n### 1. Core Data Fields to Capture  \n\n| Category | Required Fields (Why) |\n|----------|-----------------------|\n| **Identification** | Institution name, registration number, CBE/FRA license number, legal entity type (bank, NBFC, fintech, sandbox participant). |\n| **Contact & Location** | Head‑office address, city, phone, email, website URL. |\n| **Regulatory Status** | Supervising authority (CBE or FRA), sandbox cohort (if any), date of latest licence/renewal, any pending sanctions. |\n| **Financial Services** | Primary services (payments, lending, asset‑management, e‑money), API availability flag, Open‑Banking scope (account‑info, payment‑initiation). |\n| **Technical Endpoints** | Public API base URL, Swagger/OpenAPI spec link, instant‑payment network identifier (if applicable). |\n| **Publication Metadata** | Source URL, extraction timestamp, document type (PDF, HTML, press release). |\n| **Compliance Flags** | Personal‑data protection officer name, data‑retention policy note, last compliance audit date. |\n\nThese fields map directly to the information disclosed on the CBE’s **banks‑list PDF** and the FRA’s sandbox participant tables (source 1 PDF, source 2 PDF, source 3 sandbox page).  \n\n---\n\n### 2. Official‑Source Prioritisation  \n\n1. **CBE Central Registry** – the definitive list of banks and licensed payment‑system operators (PDF “Operating Banks Registered with the Central Bank of Egypt” and the “Licensing” page). This is the first stop for any bank‑type record.  \n2. **FRA Sandbox Registry** – the live roster of non‑bank financial services (NBFS) and fintech firms approved for sandbox testing (source 2 and 3).  \n3. **CBE Open‑Banking & Instant‑Payment Network Documentation** – API standards and network participant lists (source 4, source 5).  \n4. **Official Press Releases & Publications** – announcements of new licences, revocations, or regulatory updates posted on the CBE or FRA news portals.  \n5. **Regulatory PDFs & Decrees** – detailed licensing rules, e‑money definitions, and sandbox cohort‑specific guidance (source 4 of the second batch).  \n6. **Secondary but Trusted Sources** – industry directories (e.g., Egypt‑Business.com) only when the above are silent, and always cross‑checked against the primary registers.  \n\nThe hierarchy ensures that every datum originates from a government‑issued artifact before any third‑party corroboration.\n\n---\n\n### 3. Technical Blueprint  \n\n#### 3.1 Language & Encoding Handling  \n\n- **UTF‑8** is the safe default for both Arabic and English content; the Central Bank’s PDFs and web pages are UTF‑8 encoded, and the language‑specific guidance confirms its adequacy [1].  \n- When a page declares a different charset (e.g., Windows‑1256), I detect it with `chardet` and re‑encode to UTF‑8 before storage.  \n- For right‑to‑left (RTL) scripts, I preserve the original Unicode order; rendering is left to downstream consumers.  \n\n#### 3.2 Access & Legal Compliance  \n\n1. **Robots.txt & Rate‑Limiting** – I first fetch ` and ` and obey the `Crawl‑Delay` directives.  \n2. **User‑Agent Identification** – a custom UA string includes contact details, as recommended for public‑sector crawling.  \n3. **Data‑Protection Safeguards** – the Personal Data Protection Law (Law 151/2020) mandates a Data Protection Officer and encryption of any personal data at rest (source 5 PDF). I therefore encrypt the database fields that may contain personal contacts and keep an audit log for 180 days as required by Cybercrime Law 175 (source 7).  \n4. **Permission for PDFs** – the CBE’s PDFs are publicly downloadable; no additional licence is needed, but I still cite the source URL in the metadata.  \n\n#### 3.3 Crawler Architecture  \n\n| Component | Role | Implementation Note |\n|-----------|------|----------------------|\n| **Scheduler / URL Frontier** | Maintains a priority queue of official URLs (CBE banks‑list PDF, FRA sandbox page, API docs). | Uses a weighted priority queue; banks‑list gets highest weight because it changes rarely, sandbox pages get medium weight for weekly refresh. |\n| **Downloader** | Issues HTTP GET with retry‑backoff, respects `Retry‑After`. | `requests` with `urllib3` retry strategy; for large PDFs stream‑download to avoid memory spikes. |\n| **Parser** | Extracts structured fields. | - **HTML**: `BeautifulSoup` with CSS selectors. <br> - **PDF**: `pdfminer.six` for text extraction; if text is image‑based, fall back to `PyMuPDF` + `ArabicOCR` (source 10) to OCR Arabic characters. |\n| **Language Normaliser** | Detects Arabic vs. English, normalises Unicode (NFKC). | Uses `langdetect` and `arabic_reshaper` + `python-bidi` for any display‑only processing. |\n| **Data Store** | Relational DB (PostgreSQL) for structured fields; JSONB column for raw source blobs. | Encryption at column level for personal data; indexes on licence number and source URL for fast deduplication. |\n| **Updater** | Scheduler re‑crawls based on source change frequency (see § 4). | Implements ETag/Last‑Modified checks to avoid unnecessary downloads. |\n| **Error Handler** | Logs HTTP errors, parsing exceptions; exponential back‑off; alerts via email for repeated failures. | Stores error logs for 90 days to satisfy audit requirements. |\n\n#### 3.4 Data Extraction Techniques  \n\n- **Bank Lists (PDF)** – parse the table rows to pull *Name, Registration Date, Head‑Office Address* (source 1 PDF).  \n- **Sandbox Participants (HTML)** – locate the “Cohort” table on the FRA sandbox page, read *Company Name, Sandbox Cohort, Start Date* (source 3).  \n- **API Specs** – scrape the Open‑Banking API catalogue for endpoint URLs and version numbers (source 4).  \n- **Press Releases** – use RSS feeds (if available) or scrape the “News” section, extracting headline, date, and linked PDF/HTML content.  \n\nAll extracted rows are de‑duplicated by a composite key of *institution name + regulator*.\n\n#### 3.5 Update Frequency & Refresh Logic  \n\n| Source | Typical Change Cadence | Refresh Strategy |\n|--------|------------------------|------------------|\n| **CBE Banks‑List PDF** | Quarterly (official gazette) | Check `Last‑Modified` weekly; download if newer. |\n| **FRA Sandbox Page** | Every 1–2 months (new cohorts) | Crawl weekly; compare row hashes. |\n| **Open‑Banking API Registry** | As new APIs are approved | Daily ETag check; pull full spec on change. |\n| **Press Releases** | As‑issued | RSS polling every 6 hours; store new items. |\n\nThe scheduler tags each record with an `extracted_at` timestamp; downstream consumers can filter on “freshness ≤ 30 days”.\n\n#### 3.6 Error‑Handling & Resilience  \n\n- **HTTP 429 / 503** → back‑off 30 seconds, then retry up to 5 times.  \n- **Parsing Failures** → log raw payload, flag for manual review; re‑run parser after fixing extraction rules.  \n- **PDF Corruption** → fallback to a secondary mirror (if any) or send an alert to the compliance team.  \n- **Legal Breach Detection** – a watchdog script scans logs for any attempt to scrape disallowed paths (detected via robots.txt) and aborts the job immediately.  \n\n---\n\n### 4. Regulatory Constraints to Embed  \n\n1. **Data‑Protection Law (Law 151/2020)** – any personal data (e.g., contact emails) must be processed with explicit consent or a legal basis; I therefore store only publicly disclosed contact info and mark it as “public‑source”. The law also imposes fines for mishandling (EGP 100 k–1 M) (source 5 PDF).  \n2. **Cybercrime Law 175/2018** – mandates retention of IP addresses, browsing activity, and metadata for 180 days and obliges the provider to furnish them to authorities on request (source 7). My crawler logs request IPs and timestamps, retaining them in a secure audit table for the required period.  \n3. **CBE Sandbox Rules** – only “mature” fintech solutions may enter the sandbox; the sandbox only accepts fully‑functional prototypes (source 3). I therefore flag sandbox participants as “sandbox‑approved” only after confirming their inclusion on the official list.  \n4. **FRA Sandbox Decrees** – the FRA’s 2023–2024 decrees define licensing and operational requirements for NBFS; any entity not listed in the official decree PDF is excluded from the dataset (source 4 of second batch).  \n5. **Open‑Banking Regulation (in development)** – while the framework is still being finalised, the CBE requires secure API access and Strong Customer Authentication for third‑party providers (source 5). I capture the presence of SCA‑compliant APIs as a Boolean flag.  \n\nAll these constraints are baked into the crawler’s **policy engine**: before persisting a record, the engine checks that the source URL is on the approved list, that the data does not contain non‑public personal identifiers, and that the extraction respects the `robots.txt` directives.  \n\n---\n\n### 5. Step‑by‑Step Implementation Checklist (First‑Person)  \n\n1. **Map the Source Landscape** – I listed every CBE and FRA URL that publishes institution data (banks‑list PDF, sandbox HTML, API catalogue, press‑release RSS).  \n2. **Define the Schema** – I built a PostgreSQL table matching the fields in § 1, adding `source_url`, `extracted_at`, and `raw_blob`.  \n3. **Set Up the Scheduler** – using `APScheduler`, I created jobs for each source with the frequencies in § 3.5.  \n4. **Write the Downloader** – a thin wrapper around `requests` that reads `robots.txt`, respects `Crawl‑Delay`, and records request metadata for audit.  \n5. **Parse PDFs** – I employed `pdfminer.six` to pull text; when the PDF is image‑only, I call `ArabicOCR` to OCR Arabic characters (source 10).  \n6. **Parse HTML** – `BeautifulSoup` selectors target the sandbox tables and API listings; I normalise Arabic text with `arabic_reshaper` + `python-bidi`.  \n7. **Validate & De‑duplicate** – each record is hashed; duplicates are ignored unless the source timestamp is newer.  \n8. **Encrypt Sensitive Columns** – using PostgreSQL’s `pgcrypto`, I encrypt fields that may contain personal contact data.  \n9. **Log & Retain** – every crawl attempt writes a row to an `audit_log` table; logs are kept for 180 days per Cybercrime Law 175.  \n10. **Monitor & Alert** – I configured Slack alerts for HTTP 4xx/5xx spikes, parsing errors, and any attempt to access disallowed URLs.  \n\n---\n\n### 6. Putting It All Together  \n\nBy **starting with the CBE’s official banks‑list PDF** and the **FRA sandbox participant page**, I ensure the crawler’s backbone is anchored to the highest‑trust sources. The **layered architecture** (scheduler → downloader → parser → validator → store) isolates each concern, making it easy to add new official feeds (e.g., future Open‑Banking API registries) without rewriting the whole system.  \n\nThe **regulatory overlay**—data‑protection officer, encrypted storage, audit‑log retention, and strict robots‑txt compliance—keeps the operation within Egyptian law, avoiding the heavy fines outlined in the Personal Data Protection Law and the Cybercrime Law.  \n\nFinally, the **update cadence** mirrors the publishing rhythm of each source, guaranteeing that the dataset stays “up‑to‑date” while limiting unnecessary traffic to government servers.  \n\nWith this design, I can reliably harvest, normalise, and serve a live catalogue of every financial institution supervised by the CBE and FRA, ready for downstream analytics, compliance monitoring, or open‑banking integration.\n\n---\n\n### Sources\n- [1] https://www.scrapehero.com/language-encoding-web-scraping\n"
